One line per decision: what, and why.

The PDF reference board and the interface / trade-card / order-flow / forecast videos were not provided; Stage 1 follows the text descriptions. Only the God's Eye and alt-data videos were supplied.
- 26 Nov 2026 · Engine: FastAPI + uvicorn on 127.0.0.1:8787 only, SQLite in WAL mode (no DuckDB: nothing needed it yet), APScheduler BackgroundScheduler for jobs.
- Engine: every POST needs an `X-NSQ-Client` header and sensitive endpoints need a session token, so a web page cannot drive the local engine; `/kill` needs no login so it always works.
- Engine: one random data key per desk, wrapped by Argon2id keys from the password and from the recovery code; a password reset never loses encrypted data. The 6-digit PIN only unlocks the screen, never data.
- Engine: licences are `NSQ1.<payload>.<Ed25519 sig>`, checked offline; strategy packs use the same NSKO key with the `NSQPACK1` prefix and install into the Lab only. The private key lives in `tools/keys/` (git-ignored).
- Engine: vault falls back to an AES-GCM file keyed by the signed-in user's data key (or a Docker-secret passphrase on servers) when no OS keychain exists.
- Engine: the risk gate is always on in live, and live limits are clamped to hard caps (2 % per trade, 5 % daily, 10 % weekly, 10 trades, 4 open, 4 % per market) whatever the settings say.
- Engine: the multi-agent debate runs only after the risk gate passes and can only answer take or veto.
- Engine: execution never leaves a position without a broker-side stop; if a stop cannot be placed and verified after 3 idempotent retries, the position is closed.
- Engine: Time Machine and forecast fallback use a block bootstrap (blocks of 8 bars) of the market's own recent bars; when stop and target are both touched in one simulated bar, the stop counts first.
- Engine: brokers whose docs could not be reached from the build machine (Capital.com, IG, OANDA) and MT5 (Windows-only package) ship as "coming soon" with the reason. Alpaca, Kraken, Coinbase (official SDK) and IBKR (ib_async) were verified from live probes and SDK source.
- Engine: Kraken spot has no bracket orders; the stop is always broker-side and the target falls back to engine-side if Kraken refuses a second exit order. Gold on Kraken is the PAXG/USD proxy.
- Engine: Windows service uses NSSM (public domain) rather than WinSW (MIT): simpler to script, no XML.
- Engine: paper account currency is GBP with fixed FX rates in settings until a live FX feed exists.

## Stage 2 · desktop shell and UI wiring (26 Nov 2026)

- Tauri 2 shell in `app/src-tauri`: app id `uk.co.nsko.quant`, product "NSKO QUANT", version 0.2.0, window 1600×960 (min 1280×800), background #08080F. Tauri over Electron: a ~10 MB installer instead of ~100 MB, and the OS webview.
- Closing the window hides it to the tray; only the tray's "Quit engine…" (with a confirmation) exits. The engine is a separate process, so the window never decides whether trading continues.
- Tray colour comes from the shell polling `GET /health` every 4 s in Rust (green trading, amber paused, red problem / kill switch / engine not answering). Polling in Rust means the colour is right even when the window is hidden.
- Tray Kill switch and Quit engine confirm in a native dialog (tauri-plugin-dialog), not in the webview, so they work with the window closed. The desk's own confirmations use an in-app modal, because `window.confirm` is not reliable in every desktop webview.
- Engine start order: if something already answers on 127.0.0.1:8787 (the OS service), use it; otherwise start the bundled sidecar `nsko-quant-engine` (PyInstaller, `externalBin`). The sidecar is a fallback, the OS service is the intended 24/7 path.
- Broker keys: `keyring` crate (macOS Keychain, Windows Credential Manager, Linux Secret Service), service name `uk.co.nsko.quant`, account `broker:<id>:<demo|live>:key|secret`. The webview can store and delete a key but has no command to read one back; the engine reads it with Python `keyring` using the same names. `POST /brokers/{id}/connect` gets the keychain reference, not the secret.
- Assumed engine contract additions (for the engine agents): `POST /withdraw/helper {action: pause|close_positions|rescale|resume}` next to `GET /withdraw/helper`; `POST /kill {action:"release"}` re-enables trading; `POST /engine/shutdown` for the tray's Quit engine; `GET /health` returns `{status, paused, killed, account_exists}`; login errors as `{detail:{code:"totp_required"|"pin_required"|..., msg}}`; 2FA set-up via `POST /account/totp/begin` and `/account/totp/confirm`; `GET /licence/check?key=`; desk export/restore as base64 JSON (`data_b64`) with a passphrase; CORS must allow the Tauri origins (`tauri://localhost`, `http://tauri.localhost`) and the Vite dev origin.
- One event handler: the demo simulator and the engine WebSocket both call `handle(ev)` in `store.ts`, so every page works the same on both sources. Switching to the engine clears the simulator's numbers so demo and real values never mix under the ENGINE chip.
- Source default: the desktop app starts on "Live engine", a plain browser on "Demo data" (sales demos, the video ad). The choice is remembered per machine. If the engine does not answer, the desk falls back to demo data with a notice and keeps retrying with backoff (1 s → 30 s).
- Every REST call degrades the same way (`src/api.ts`): demo mode returns demo data; engine offline returns demo data plus a notice; engine errors are shown as errors, never replaced by demo data.
- Lock screen in engine mode: password first, then authenticator code or PIN when the engine asks for it. The session token lives in memory only (never localStorage), so a restart always asks again.
- God's Eye on CesiumJS 1.147 (Apache-2.0) with `Ion.defaultAccessToken = undefined`, no geocoder, no ion assets, no Google 3D Tiles, ellipsoid terrain. Basemaps: Esri World Imagery (default), OpenStreetMap standard tiles, or the Natural Earth II imagery bundled inside CesiumJS (always underneath, so the globe works offline).
- Placeholder: Esri World Imagery and tile.openstreetmap.org are fine for development and low use, but both have terms for commercial apps (Esri: an ArcGIS Location Platform account/key for commercial use; OSM: the tile usage policy forbids heavy use and asks commercial apps to use a tile provider). Before sale, move to a paid/keyed provider (e.g. Esri Location Platform, MapTiler, Stadia) or self-hosted tiles.
- Sensor modes are Cesium post-process stages: the built-in night-vision stage and a custom thermal palette shader, so they affect only the globe, not the panels.
- Code-splitting with React.lazy: Agent Room (three.js), God's Eye (CesiumJS, ~4 MB chunk) and Live Desk (lightweight-charts) load only when opened. The first bundle is ~500 kB.
- CI (`nsko-quant/.github/workflows/build.yml`) uses free runners: ubuntu-22.04, windows-latest, macos-15 (Apple Silicon) and macos-15-intel. It must be copied to the repo root `.github/workflows/` to run while NSKO QUANT lives inside the nsko-solutions repo.
- macOS universal: PyInstaller cannot make one universal2 binary with numpy/pandas, so the universal `.app` carries both engines as resources and a 5-line launcher (the sidecar) picks the one for the Mac's CPU.
- Builds are unsigned for now. Signing steps for later:
  - macOS: Apple Developer Program (£79/yr) → "Developer ID Application" certificate → set `APPLE_CERTIFICATE` (base64 .p12), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, and for notarisation `APPLE_ID`, `APPLE_PASSWORD` (app-specific password) and `APPLE_TEAM_ID` as GitHub secrets; tauri-action signs and notarises. The two engine binaries inside Resources must be signed with the hardened runtime too (add a `codesign --options runtime` step before bundling).
  - Windows: an OV or EV code-signing certificate (or Azure Trusted Signing) → `bundle.windows.certificateThumbprint` / `signCommand` in tauri.conf.json, and sign `nsko-quant-engine.exe` with the same certificate, otherwise SmartScreen warns.
  - Linux: optional; AppImage can be GPG-signed (`SIGN=1`, `APPIMAGETOOL_SIGN_PASSPHRASE`).
  - Updater: run `npx tauri signer generate`, put the public key in `plugins.updater.pubkey`, keep the private key as `TAURI_SIGNING_PRIVATE_KEY` (+ password) secrets, set `bundle.createUpdaterArtifacts: true`, and host `latest.json` at the real feed URL (placeholder now: `https://updates.example.com/nsko-quant/latest.json`).
- Placeholder: the update feed URL and updater public key are placeholders; "Check for updates" says "Update feed not set up yet" until they are real.
- Stage 3 · `candles.get` tries sources in this order: broker providers, then the CSV cache, then Kraken public OHLC, then seeded synthetic data. `df.attrs` records the source, `synthetic`, `volume_kind` and `partial`. Kraken OHLC returns only the latest 720 bars, so deeper crypto history comes from a polite backfill from Kraken's Trades endpoint.
- Stage 3 · Synthetic candles use GARCH(1,1) with Student-t shocks, an intraday activity curve and the weekend close. They are seeded per market and timeframe and built one year at a time, so a longer window never rewrites earlier bars. Synthetic Lab results never create a strategy.
- Stage 3 · Gold order flow is a tick-volume profile, labelled as such in every payload. CFDs give no exchange volume. Only crypto gets bubbles, from Kraken WS v2 trades, with same-timestamp taker trades merged into one aggressive order.
- Stage 3 · Signals are stamped at the open time of the closed bar and fill at the next bar's open. NSKO-OF-1 takes the lower timeframe as input. It builds higher-timeframe levels only from completed bars, and a higher-timeframe FVG becomes usable only once its bar has closed. Every generator and detector is tested for look-ahead.
- Stage 3 · The backtester assumes the stop is hit first when a bar touches both, fills gaps at the open, and works in R with compounding at `lab.risk_pct`. Cost profiles per market type live in `lab.costs.<kind>`; crypto commission defaults to 10 bps per side, which is honest and kills most 5-minute crypto scalps.
- Stage 3 · The bar and all overfitting thresholds are `lab.bar.*` settings: OOS Sharpe 1.40, 30 OOS trades, 20 % drawdown, ±20 % stability ratio 0.5, PBO ≤ 0.5 (CSCV, 16 blocks over the 10 variants), IS→OOS decline ≤ 0.6, and beating at least 90 % of random entries. Robustness checks run only on variants that already pass the primary bar, to save compute.
- Stage 3 · Research uses local Ollama when it is running (reusing `debate.ollama_*` unless `research.ollama_*` is set). Otherwise it uses a deterministic offline summariser. The budget is counted in "think units" (about 1 per 1,000 local tokens; offline steps cost 0.05).
- Stage 3 · Source policy: only headlines and links from news, and robots.txt is checked before any page fetch. The XML parser refuses DTDs. Congressional PTRs are off by default, because US law bars commercial use. Senate eFD is a link only. YouTube transcripts are off by default because of the YouTube terms.
- Stage 3 · God's Eye uses free layers only. Ships (AISStream), fires (FIRMS), EIA and YouTube are bring-your-own-key, read from the keychain or `NSQ_<NAME>` and never stored in settings. Open-Meteo's free API is non-commercial, so a paid product must use the customer API (`open_meteo_api_key`).
- Stage 3 · MARKET IMPACT never trades. Risk actions are suggestions unless `godseye.risk_actions = "apply"`; applied ones are written to `godseye_risk_flags`, which can only reduce risk, for the risk gate to read. Synthetic layers never raise alerts.
- Stage 3 · Crop Watch V1 uses cloud-adjusted Sentinel-2 `s2:vegetation_percentage` from Planetary Computer STAC as an NDVI stand-in. Pixel NDVI with rasterio is left for later. Car Counts is a locked premium placeholder.
- Stage 3 · The Knowledge Base, with its detectors and 6-step lifecycle, lives in `nsq/lab` next to the code that uses it. Research's TERM-CHECKER feeds it at step "found".

## Stage 4 · integration of the engine and the desk (26 Nov 2026)

- One place maps engine shapes to desk shapes: `app/src/api.ts`. The engine keeps its own clean shapes; where the desk's assumption was cleaner or a real need (batch settings, JSON backup, withdraw steps, pause, rollback to a chosen version), the engine grew the endpoint. Full table in `engine/CONTRACT.md`.
- Re-enabling after the kill switch is `POST /trading/enable` (needs the login), not `/kill {action:"release"}`: stopping must be easy, starting again must be deliberate.
- The tray authenticates with a local shared secret (`<data_dir>/shell.token`, random per engine start, owner-only), not with "anything from localhost": any local web page can reach localhost, but cannot read that file. The kill switch needs no secret and no login.
- New "pause new trades" (`trading.paused`): a softer stop than the kill switch. Open trades keep their broker-side stops and are still managed. Used by the tray, Settings and the withdraw helper.
- The WebSocket needs the session token (`/ws?token=`): it carries account and trade data.
- Every state-changing POST of the data / research / Lab / God's Eye routers needs a signed-in session; reading stays open on localhost.
- The engine refuses to listen on a non-local address unless `NSQ_ALLOW_NON_LOCAL=1` (set only inside the Docker image, which publishes on the host's 127.0.0.1).
- CI and the Tauri sidecar use a ONE-FILE PyInstaller build (`engine/nsko-quant-engine.spec`), because Tauri's `externalBin` needs a single executable; the one-folder spec in `deploy/pyinstaller/` stays for the OS services.
- The CI workflow runs from the repo root (`/.github/workflows/nsko-quant-build.yml`); the copy in `nsko-quant/.github/` is a reference kept identical. Engine tests now run before the build; `--version` is a hard smoke test.
- In engine mode the engine's scripted demo source runs only when no data feeds are configured. With feeds on (the default: XAU/USD and BTC/USD 1-minute candles, Kraken trade stream), the desk shows real or clearly synthetic-flagged data, never a scripted cycle under the ENGINE chip. If the engine does send demo-flagged events, the desk shows "ENGINE DEMO FEED".
- Engine-mode pages draw only what the engine sends; when there is nothing yet they say so ("Waiting for the scanner", "No Lab results yet") instead of drawing demo lines. Demo mode is unchanged.
- The Lab fan in engine mode shows each variant's stored equity curve as % return over the whole test window (the real split date varies per run, so the demo's fixed IS/OOS halves are not drawn).
- JARVIS chat goes through the engine (`POST /jarvis/chat`): the local model through Ollama when it runs; otherwise a plain "the local model is not installed" with install steps and only facts the engine knows. It never invents an answer and cannot place trades.
- A development-only trade trigger (`POST /dev/run-demo-trade`) exists only when the engine starts with `NSQ_DEV=1`, still needs a login, and runs the real flow on seeded synthetic candles with a test signal, flagged synthetic everywhere. It must never be set in a shipped build.
- Telegram pairing is a one-time 6-digit code the user sends to their own bot as `/pair 123456` (10 minutes, 5 tries, only a hash is stored); the bot token goes into the vault / OS keychain and can never be read back through the API.
- God's Eye risk flags reach the risk gate only when the user chose "Apply": `pause_new` blocks a new entry on that market, `cut_size` multiplies the size by `godseye.cut_size_factor` (default 0.5). They can only reduce risk, and God's Eye still never opens a trade.
- The demo broker list matches the engine's catalogue (Paper connected; Capital.com, IG, OANDA and MT5 "coming soon" with the reason), so a sales demo never promises a broker the engine cannot use.
- Live start size is a setting (`live.start_size_pct`, default 50 %, clamped 10–100 %) instead of a fixed 50 %.
- Strategy updates mode is a setting (`updates.mode`: manual / auto_paper (default) / ask), matching the desk's three choices.
